# Marazmati4ka — блокнот

Личный веб-блокнот поверх папки `docs/`: промпты, инструкции, подборки, заметки, шпаргалки.

Первая версия крутится на своём компьютере (`localhost`). Позже тот же код можно выложить как обычный Node-сервер (Fly, Railway, VPS). Не целимся в Vercel: там файловая система только для чтения.

## Для кого

Один пользователь — ты. Не аккаунты, не лента, не «соцсеть промптов». Открыл — нашёл — скопировал или дописал.

## Хранение: инфоблок + файл параллельно

Как в Битриксе. Элемент инфоблока и физический файл — **две параллельные сущности**, не одна разрезанная пополам.

- Элемент живёт в базе сам по себе: `ID`, поля, `DETAIL_TEXT`, активность. Без файла он всё равно элемент.
- Файл живёт на диске сам по себе. Без строки в базе он просто файл, пока его не импортировали.
- **Приоритет у базы.** Интерфейс читает и пишет элемент. Файл — проекция элемента, не источник правды.
- Если база и файл разошлись — побеждает элемент. Файл перезаписывается из БД (или помечается «расхождение»), диск сам карточку не ломает.

| | Инфоблок (`notes`) | Файл `.md` |
|---|---|---|
| Это | элемент: id, свойства, полный текст | параллельная копия на диске |
| Обязателен? | да, без него в блокноте ничего нет | нет |
| Кто главный | да | нет |
| Зачем | сайт, поиск, фильтры, правка, корзина | git, Obsidian, бэкап папки |

Аналогия точнее: инфоблок «Заметки», у элемента свойства `TYPE` / `DOMAIN` и поле `DETAIL_TEXT` (весь markdown). Файл в `docs/...` — как приложенный или выгруженный детальный файл, а не «настоящая» заметка.

### Что канонично где

- **Полный текст** — в базе (`body`), как `DETAIL_TEXT`. Открытие `/n/42` читает строку, не диск.
- **Карточка** — в базе: `id`, type, domain, title, source, active, даты. URL — `/n/42`.
- **Файл** — зеркало: пишется *после* успешного сохранения элемента. Нет файла → элемент всё равно открывается. Нет элемента → файл в библиотеке не виден, пока не импортирован.
- **Путь** — удобный адрес зеркала (`docs/<type>/<domain>/<slug>.md`), не идентификатор.

### Схема элемента (`notes`)

```
id              integer PK
title           text
type            text        -- prompt | guide | catalog | article | reference
domain          text        -- image | video | copy | ...
slug            text
body            text        -- полный markdown, канон
source          text null
snippet         text
prompt_extract  text null
path            text null   -- зеркало; null = файла ещё нет
file_hash       text null   -- hash последней выгрузки из БД
file_mtime      datetime null
active          boolean     -- 0 = в корзине (элемент не удаляем)
created_at      datetime
updated_at      datetime
```

База в v1 — **SQLite** (`data/notebook.db`). На VPS позже тот же инфоблок можно перенести на Postgres.

### Как пишем и как синхронизируем

1. **Из интерфейса (основной путь)**  
   Сначала `INSERT`/`UPDATE` элемента. Потом, если получилось, выгрузить зеркало в `.md`.  
   Файл не записался — элемент жив, в карточке пометка «зеркало не записалось».  
   Смена типа/области — меняем поля элемента, затем перекладываем файл. Не наоборот.

2. **Импорт с диска (явный, не автоперезапись)**  
   Первый запуск и кнопка «Импортировать файлы»: обход `docs/**/*.md`.  
   - файла нет в базе → создать элемент, `body` = содержимое файла  
   - файл есть, hash совпал с `file_hash` → ничего  
   - файл есть, hash другой → **не затираем элемент**. Показать «файл новее зеркала», импорт только по подтверждению  
   Пропавший файл элемент **не деактивирует**. Зеркало просто отсутствует.

3. **Корзина**  
   `active=0`. Зеркало уезжает в `_trash/` если было. Элемент остаётся в инфоблоке.  
   Восстановление — `active=1` и снова выгрузить файл.

Текущий архив — разовый импорт: ~580 файлов становятся ~580 элементами. После этого канон — база. Папка `docs/` остаётся живой копией для git и внешних редакторов, но не командует блокнотом.

## Иллюстрации

Та же битриксовая схема, что у заметок: **запись о файле в базе + байты на диске**. Картинка не живёт внутри markdown и не как BLOB в SQLite.

Как `b_file` + `PREVIEW_PICTURE` / галерея свойств: элемент ссылается на файлы по `id`. Без картинки элемент нормальный. Файл на диске без строки в `files` — просто мусор в папке, пока не привязан.

Нужно в первую очередь промптам `domain=image`: на полке видно «что получилось», в карточке — результат и референсы. Тот же механизм у видео-превью, гайдов, любых заметок.

### Роли (свойства файла у элемента)

| role | Как в Битриксе | Зачем |
|---|---|---|
| `cover` | `PREVIEW_PICTURE` | обложка в библиотеке; у элемента одна |
| `result` | галерея «результат» | что вышло из промпта; несколько |
| `reference` | галерея «референс» | вход, стиль, лицо, исходник |
| `inline` | файл из текста | картинка, на которую ссылается `body` |
| `attachment` | приложенный файл | схема, pdf-скрин, прочее |

Для графического промпта типично: одна `cover` (лучший кадр) + пачка `result` + по желанию `reference`.

### Диск

```
data/media/<note_id>/<file_id>.<ext>
```

Имя на диске — `id` файла, не «красивое». Оригинал сохраняем как есть (png/jpg/webp). Для полки при загрузке делаем превью `data/media/<note_id>/<file_id>.cover.webp` (длинная сторона ≤ 800). В базе оба пути.

Не кладём картинки в `docs/` рядом с зеркалом `.md`: зеркало текста и медиа — разные деревья. В выгруженном markdown ссылка вида `![](/media/184)`.

### Таблица `files` (как `b_file`)

```
id              integer PK
orig_name       text
mime            text
ext             text
bytes           integer
width           integer null
height          integer null
path            text        -- оригинал
preview_path    text null   -- .cover.webp
hash            text
created_at      datetime
```

### Привязка `note_files`

```
id              integer PK
note_id         integer  → notes.id
file_id         integer  → files.id
role            text     -- cover | result | reference | inline | attachment
sort            integer  -- порядок в галерее
```

У элемента поле `cover_file_id` — удобный ярлык обложки (как `PREVIEW_PICTURE`). Это тот же файл, что в `note_files` с `role=cover`. Смена обложки = смена этого id + роли.

### Что канонично

- **Метаданные и привязка** — база. Сайт отдаёт `/media/<file_id>`.
- **Байты** — диск. SQLite картинки не хранит.
- **Текст** — в `notes.body` без base64. При импорте старых `.md` выдираем `data:image/...` в `files`, в `body` ставим `![](/media/<id>)`.
- Пропала картинка с диска — элемент жив, слот «файл недоступен». Пропала строка в `files` — байты на диске библиотека не показывает.

### В интерфейсе

- Библиотека: если есть `cover` — плитка с картинкой; иначе текстовая карточка. Фильтр «графика» почти весь в плитках.
- Карточка промпта: сверху обложка и галерея `result` / `reference`, ниже текст и «Скопировать промпт».
- Редактор: загрузка в нужную роль, drag-and-drop порядка, «сделать обложкой».
- Чужой тип (гайд, аналитика) — тот же загрузчик, просто роли реже нужны.

### Как прикрепляется картинка

Два равноправных входа, один пайплайн (`POST /api/files` → `files` + `note_files`). Не вставляем base64 в текст.

1. **Диалог файла**  
   Кнопка «Выбрать картинку» → системный `Open file`. Можно несколько файлов сразу. `accept` — jpeg, png, webp, gif.

2. **Ctrl+V (и ⌘V)**  
   Ловим `paste` на странице редактора. Из буфера берём:
   - `image/*` — скриншот, копия из браузера / мессенджера / редактора;
   - скопированный файл картинки из проводника (`clipboardData.files`).  
   Если в буфере только текст — обычная вставка в поле, картинку не ищем.

3. **Видео из файла**  
   Кнопка «Выбрать видео» → системный диалог. Форматы mp4, webm, mov, до 500 МБ. Ролик играется в галерее, в текст и в обложку не ставится. Ctrl+V с файлом видео из проводника работает так же.

Куда вешаем роль при вставке:

| Где фокус / куда навели | role |
|---|---|
| слот обложки | `cover` (старую обложку снимаем) |
| галерея «результат» | `result` |
| галерея «референс» | `reference` |
| поле текста | `inline` + в курсор `![](/media/<id>)` |
| страница редактора без зоны | `result` для `domain=image`, иначе `attachment`; если обложки нет — первая картинка ещё и `cover` |

Новая заметка: `/new` сразу создаёт черновик-элемент (`draft=1`), чтобы у загрузки был `note_id`. Отмена без сохранения — черновик и его файлы в корзину.

Картинки режутся по типу и 15 МБ, видео — по типу и 500 МБ. Ошибка показывается рядом с галереей, не молча.

### Ограничения v1

- Картинки: jpeg, png, webp, gif, потолок 15 МБ.
- Видео из файла: mp4, webm, mov, потолок 500 МБ. Ролик хранится как обычный файл заметки и играется в галерее. Обложкой его не ставят: на полке по-прежнему картинка.
- Документы: PDF, потолок 50 МБ. Роль `attachment`, список в конце карточки, не галерея и не обложка.
- Больше лимита — отказ с понятной ошибкой.
- Не тянем картинки по URL сами (кроме явного «сохранить превью» позже).

## Таксономия

Типы и области — справочники в базе (`taxons`), как разделы инфоблока. Стартовый набор засевается при первом запуске, дальше правится в UI: `/settings`.

- **Название** — что видно в фильтрах и карточках
- **Код (slug)** — у типа путь зеркала; у области — множественная привязка (`note_domains`). Зеркало лежит в первой выбранной области: `docs/<type>/<primary-domain>/`
- Смена кода перекладывает связанные заметки (поле + папка)
- Удаление, если справочник занят, требует переноса записей на другой пункт

Не в v1: вложенные разделы, права на справочник.

## Экраны

### 1. Библиотека `/`

Слева или сверху: поиск + фильтры по типу и области (можно несколько).  
Справа: список карточек — обложка если есть, заголовок, тип, область, сниппет.

Пустой поиск + фильтр «Промпт / Графика» = полка с визуальными промптами.

### 2. Заметка `/n/<id>`

- Галерея иллюстраций (обложка, результаты, референсы)
- Markdown как читаемый текст
- Для `prompt`: кнопка «Скопировать промпт» берёт первый fenced-блок (```), иначе всё тело
- Источник, если есть
- Правка и удаление

### 3. Редактор `/new` и `/n/.../edit`

Поля: заголовок, тип, область, источник (необяз.), текст, иллюстрации (роли cover / result / reference).  
Сохранение пишет элемент, затем выгружает зеркало. Смена типа/области — поля элемента, потом перенос файла. Картинки остаются на `note_id`, папка `data/media/<id>/` не переезжает.

Удаление: подтверждение, `active=0`; зеркало в `_trash/`, если было.

### 4. Поиск

Один инпут. Список и фильтры — SQL по элементам.  
Полнотекст: FTS5 по `title` + `body`. Файл в поиске не участвует.

## Что умеет v1

- Просмотр списка и одной заметки
- Поиск + фильтры тип/область
- Добавление
- Правка
- Удаление в `_trash/`
- Копирование промпта одной кнопкой
- Иллюстрации: диалог файла и вставка Ctrl+V, обложка, галерея результатов/референсов
- При импорте — вытащить вшитые base64-картинки из старых `.md` в `files`

Не в v1: аккаунты, избранное, теги в UI, связанные карточки, автограф/декей, картинки-превью, мобильное приложение.

## Стек

Один репозиторий, один процесс:

- **Next.js (App Router)** + React
- **SQLite** (`node:sqlite`) — инфоблок: элементы, полный текст, фильтры, FTS, корзина
- Файлы в `docs/` — параллельные зеркала текста, не канон
- Картинки в `data/media/<note_id>/` + таблицы `files` / `note_files`
- Markdown: `react-markdown` + подсветка кода
- Стили: свой CSS, без тяжёлого UI-кита

Почему не «только файлы»: блокнот работает с элементами, как админка Битрикса с инфоблоком.  
Почему файл всё равно нужен: git, внешний редактор, перенос папки. Он сосед, не хозяин.  
Почему не Vercel: нужны файл БД и том под зеркала. Деплой — Docker / `node` на VPS с томом на `data/` и `docs/`.

## Потоки

```
Первый запуск
  → создать data/notebook.db
  → импортировать docs/ → элементы (разово)

Открыть библиотеку / заметку / поиск
  → только SQL по notes (body тоже из базы)

Добавить / править
  → INSERT/UPDATE элемента + FTS
  → затем выгрузить зеркало .md
  → сбой записи файла не откатывает элемент

Удалить
  → notes.active = 0
  → зеркало в _trash/, если было

Импорт с диска (кнопка)
  → новые файлы → новые элементы
  → изменённые файлы → не трогать элемент, показать расхождение
```
