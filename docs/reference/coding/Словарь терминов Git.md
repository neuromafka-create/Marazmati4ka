Базовые понятия и локальная работа

* Репозиторий (Repo) — проект на GitHub или его локальная копия; папка, где хранится код и вся история его изменений.
* Ветки (Branches) — параллельные версии кода. Обычно ответвляются от главной ветки (`main` или master - устарело), чтобы можно было безопасно делать новые фичи или чинить баги, не ломая рабочий проект.
* Стейджинг (Staging / git add) — добавление измененных файлов в «индекс» перед коммитом.
> Пример: «Нет незастейдженных изменений» (no unstaged changes) означает, что все твои правки уже добавлены в индекс и готовы к коммиту (рабочая директория чистая).

* Коммит (Commit / Фиксация) — сохранение изменений в истории Git. По сути, это снимок состояния твоего кода с описанием того, что было сделано. *(Примечание: слово «фиксация» обычно используют именно как перевод слова commit, а вот «fix» в IT чаще означает просто исправление бага).*
* Стэш (Stash) — «временная полка» для незакоммиченных изменений. Полезно, когда один агент уже начал мерджить, в второй в это время внес изменения в мэин, и первый не знает, что делать с изменениями второго.
* Ворктрис (Worktrees) — рабочие деревья. Позволяют клонировать проект в соседнюю директорию, чтобы разные агенты могли одновременно работать с разными ветками одного репозитория.

Синхронизация с сервером

* Пуш (Push) — отправка твоих локальных коммитов в удалённый репозиторий (на GitHub).
* Ориджин (Origin) — стандартное имя (псевдоним), которое Git по умолчанию присваивает удаленному репозиторию. По сути, это просто короткий ярлык для длинного URL-адреса проекта на сервере. 
>  Пример: Команда git push origin main буквально означает «отправь мои коммиты по адресу origin в ветку main».

* Пулл (Pull / Вытягивание) — противоположность пушу. Загрузка новых изменений с сервера в твой локальный репозиторий.
> *Пример:* «Не забывай вытягивать перед началом работы» — чтобы не словить конфликты со свежим кодом твоих удаленных агентов.

* Мердж (Merge) — слияние двух веток в одну.
* Черри-пик (Cherry-picking) — «выклевывание» конкретного коммита из одной ветки/PR и точечное копирование его в свою ветку.

Совместная разработка

* Форк (Fork) — создание полной копии чужого репозитория в своем аккаунте. Делается, чтобы синхронизировать СВОИ изменения с апстримом, или сделать ПР в чужой репо.
* Апстрим (Upstream) — оригинальный репозиторий, с которого ты сделал форк.
* Ишью (Issue) — задача, обсуждение бага, предложение новой фичи или просто пост с проблемой внутри репозитория на GitHub.
* ПР (Pull Request / PR) — запрос на проверку твоего кода и вливание (мердж) твоих изменений в основную ветку чужого репозитория.
* Код-ревью (Code review / Ревью) — процесс проверки твоего ПР другими разработчиками перед тем, как его смерджат.
* Блокер (Blocker) — критическая проблема, из-за которой нельзя продолжать работу.
> Пример: «ПР #137 является блокером для ПР #238» — это значит, что пока не вольют 137-й, начинать проверку и слияние 238-го не имеет смысла (или технически невозможно).

Роли в проекте

* Мейнтейнер (Maintainer) — владелец или главный управляющий репозитория.
* Коллаборатор (Collaborator) — партнер мейнтейнера, у которого есть права на запись (редактирование, мердж) в репозиторий.
* Контрибьютор (Contributor) — человек, который внес вклад в проект (написал код, поправил документацию, сообщил о баге), но не обязательно имеет права на прямое управление репозиторием. Он автоматически получает статус контрибутора проекта пожизненно.

Пример:

Бывает так, что мейнтейнер отклоняет (закрывает) твой Pull Request со статусом «такие изменения не планируются». Делает cherry-pick твоих коммитов и присваивает все твои контрибьюции себе.

Так поступать очень некрасиво — это дурной тон. Если мейнтейнеру не нравится часть кода, правильнее было бы принять PR (чтобы сохранить авторство контрибьютора), а затем отдельным патчем сверху удалить или изменить то, что не устроило. Либо пропросить контрибутора дработать ПР.
