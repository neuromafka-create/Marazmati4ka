Когда люди впервые слышат про Git, им кажется, что это очень сложная система. На самом деле почти все его "страшные" функции можно понять на примере обычного текста в Word.

Представьте, что вы пишете книгу.

Каждый вечер вы сохраняете новую копию:

```text
Книга_v1.docx
Книга_v2.docx
Книга_v3.docx
Книга_финал.docx
Книга_финал2.docx
Книга_финал_точно.docx
```

Git делает то же самое, только намного умнее.

---

# 1. Ветки (Branches)

Самая важная возможность Git.

Представьте, что ваш проект — это дом.

Есть дом, в котором живут люди.

Он должен быть всегда пригоден для жизни.

Но вы решили перестроить кухню.

Вместо того чтобы ломать кухню прямо в жилом доме, вы строите ее копию в соседнем помещении.

Когда ремонт закончен — переносите изменения обратно.

Именно так работают ветки.

Получается примерно так:

```text
main
 │
 │
 ├───────────── рабочий проект
 │
 │
 └──── feature-chat
         │
         │
         ├─ эксперимент
         ├─ новый интерфейс
         ├─ куча изменений
```

Главная ветка называется

```text
main
```

Она должна всегда работать.

Для новой функции создают отдельную ветку.

Например

```text
feature-login

feature-payment

feature-chat
```

Вы можете хоть полностью сломать код в этой ветке.

Главный проект при этом не пострадает.

Когда всё работает —

объединяете изменения.

---

## Зачем это нужно?

Представьте:

У вас уже есть рабочее приложение.

Им пользуются люди.

Вы решили добавить чат.

Во время разработки чат ломает половину программы.

Если работать прямо в main —

сломается весь проект.

Если работать в отдельной ветке —

никто этого даже не заметит.

---

# 2. Pull Request (PR)

Название пугающее, но смысл очень простой.

Допустим, вы построили новую кухню.

Теперь говорите хозяину дома:

> Посмотри.
>
> Всё ли тебе нравится?
>
> Можно переносить?

Это и есть Pull Request.

Он означает

> "Я закончил работу.
> Проверь мои изменения."

В больших командах никто не может просто взять и изменить основной проект.

Сначала создаётся Pull Request.

Другие разработчики смотрят:

* нет ли ошибок;
* красивый ли код;
* ничего ли не сломано.

Если всё хорошо —

нажимают кнопку

```text
Merge
```

и изменения попадают в main.

---

## Если работаешь один

Pull Request всё равно полезен.

Почему?

GitHub показывает

* какие строки изменились;
* какие файлы изменились;
* что именно было удалено;
* что было добавлено.

Иногда сам смотришь свой PR и думаешь:

> "Ого... а это вообще зачем я удалил?"

---

# 3. Merge (слияние)

После того как работа закончена, ветку нужно объединить с основной.

Было

```text
main

    |

feature-chat
```

Стало

```text
main

    |

все изменения из feature-chat
```

После этого ветку можно удалить.

---

# 4. Конфликт (Merge Conflict)

Вот этого боятся все новички.

На самом деле конфликт — это вовсе не ошибка.

Git просто говорит:

> Я не понимаю, какой вариант оставить.

Например.

Было

```python
name = "Иван"
```

Вы изменили

```python
name = "Петр"
```

А коллега одновременно изменил

```python
name = "Алексей"
```

Теперь Git видит две разные версии одной и той же строки.

Он спрашивает:

> Какую оставить?

Это называется конфликт.

---

Git покажет примерно так

```text
<<<<<<< HEAD

name = "Петр"

=======

name = "Алексей"

>>>>>>> feature-login
```

Вы просто вручную выбираете правильный вариант.

Например

```python
name = "Алексей"
```

или

```python
name = "Петр"
```

или

```python
name = getCurrentUser()
```

После сохранения конфликт считается решённым.

---

## Хорошая новость

Если работаете один —

конфликтов почти никогда не бывает.

---

# 5. Теги (Tags)

Представьте игру.

Есть версии

```text
0.8

0.9

0.95

1.0

1.1

1.2
```

Когда выходит важная версия —

ей дают имя.

Например

```text
v1.0
```

или

```text
v2.3
```

Это и есть тег.

Он говорит

> "Вот именно эта версия является релизом."

---

Допустим

Сегодня у вас уже версия

```text
v3.7
```

Но клиент говорит

> Мне нужна версия,
> которая была в прошлом месяце.

Вы открываете тег

```text
v3.5
```

и получаете именно тот код.

Очень удобно.

---

# 6. Rebase

Самая загадочная команда Git.

На самом деле идея очень простая.

Представьте книгу.

История выглядит так:

```text
Глава 1

↓

Глава 2

↓

Глава 3

↓

Глава 4
```

Но вы понимаете:

Главу 2 надо было написать после главы 4.

Rebase позволяет аккуратно перестроить историю.

То есть

было

```text
A

↓

B

↓

C

↓

D
```

стало

```text
A

↓

C

↓

D

↓

B
```

Или вообще объединить несколько промежуточных коммитов в один.

---

# Зачем это делают?

Допустим, вы работали три часа.

За это время сделали коммиты

```text
Fix

Fix2

ЕщеFix

Попытка

Попытка2

Исправил

Работает

Последнее

Точно работает
```

Такая история никому не нужна.

Перед публикацией можно сделать rebase.

Получится

```text
Added authentication
```

История становится красивой и понятной.

---

## Почему rebase считают опасным?

Потому что он **переписывает историю**.

Представьте, что кто-то уже читает книгу, а вы начали менять порядок глав. Если несколько человек работают с одной и той же историей, это может вызвать путаницу.

Поэтому есть простое правило:

* **Можно** делать `rebase` для своих локальных коммитов, которые ещё не отправлены на GitHub.
* **Не стоит** делать `rebase` опубликованной истории, если этой веткой уже пользуются другие люди.

Для начинающего разработчика этого правила более чем достаточно.

---

# Что действительно нужно знать новичку?

Из всех этих возможностей я бы рекомендовал осваивать их именно в таком порядке:

1. **Ветки** — чтобы безопасно разрабатывать новые функции.
2. **Merge** — чтобы переносить готовые изменения в основную ветку.
3. **Pull Request** — чтобы проверять изменения перед объединением (даже если вы работаете один).
4. **Теги** — чтобы отмечать важные версии программы (`v1.0`, `v2.0` и т.д.).
5. **Конфликты** — научиться не бояться их и понимать, как выбрать правильный вариант.
6. **Rebase** — оставить напоследок. Он полезен, но не нужен для повседневной работы в первые недели или даже месяцы.

Если сравнить с автомобилем, то сначала учатся пользоваться рулём, педалями и коробкой передач. Турбонаддув, спортивный режим и тонкая настройка подвески изучают гораздо позже. С Git точно так же: для комфортной работы достаточно уверенно владеть базовыми командами и понимать, зачем нужны ветки. Остальные возможности можно подключать постепенно, по мере роста опыта.
